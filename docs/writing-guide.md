# 문서 작성 가이드라인

## 적용 범위
- 컨벤션, 아키텍처를 정의하는 오래 유지되는 Markdown 문서에 적용함
- 명세 항목을 담은 문서(`docs/specs/` 아래의 `README.md`가 아닌 파일)는 이 가이드 대신 [명세 작성 규칙](specs/README.md#작성-규칙)을 따름
  - 명세 문서는 nocap이 입력으로 읽는 데이터임. 사람이 읽는 설명 문서와 성격이 다름
- `AGENTS.md` 같은 agent instruction 파일, 임시 작업 노트, 생성 문서는 제외함
  - agent instruction 파일은 매 작업마다 읽히는 명령 목록임. 설명 문서와 쓰는 목적이 다름
- 패키지를 소개하는 `README.md`와 그 번역본 `README.ko.md`는 제외함
  - README는 npm과 GitHub에서 nocap을 처음 보는 사용자가 읽음. 영어 사용자도 읽어야 해서 언어별로 둠
  - README는 소개와 빠른 시작만 담음. 세부 규칙은 이 가이드를 따르는 문서에 두고 README에서 링크함

## 언어
- 문서는 한글로 씀. 문서를 언어별 쌍으로 관리하지 않음
- identifier, 파일 경로, 명령어, 설정 키, 굳어진 기술 용어는 원래 표기 그대로 둠
  - 번역하면 문서와 코드 사이의 연결이 끊어짐
- identifier, 파일 경로, 명령어, 설정 키는 백틱으로 감쌈. 예: `SpecItem`, `docs/specs/`
  - 일반 단어와 코드 요소를 눈으로 구분할 수 있어야 함

## 문장
- 문장 끝은 개조식으로 씀
  - 사실·동작: "~함", "~임". 예: "nocap은 ID 중복을 검사함"
  - 의무: "~해야 함". 예: "기여자는 ID를 확인해야 함"
  - 금지: "~하지 않음". 예: "구현 세부는 쓰지 않음"
  - 완료: "~했음". 예: "2026-11-02에 확인했음"
- 문장 끝에는 마침표를 쓰지 않음. 한 항목에 문장이 둘 이상이면 문장 사이에만 마침표를 씀
  - 목록 항목과 줄바꿈이 이미 문장 끝을 구분함
- 한 문서 안에서 개조식과 다른 문체를 섞지 않음
  - 문체가 섞이면 독자가 문체 변화에 의미가 있는지 판단해야 함
- 주어와 조사를 생략하지 않음
  - 예: "ID 중복 검사함" 대신 "nocap은 ID 중복을 검사함"
  - 주어가 없으면 누가 그 동작을 하는지 알 수 없음
- 한 문장에는 한 가지 내용만 씀
- 같은 개념은 항상 같은 용어로 부름. 동의어를 섞지 않음
- 능동태로 씀
  - 예: "ID 중복이 검사됨" 대신 "nocap은 ID 중복을 검사함"
- 단정형으로 씀. "~일 수도 있음", "아마", "~인 것 같음"을 쓰지 않음
  - 확인하지 않은 내용은 "확인되지 않음"이라고 명시함
- 모호한 표현 대신 숫자와 예시를 씀
  - 예: "느려짐" 대신 "5초를 넘음"
  - 모호한 표현은 독자마다 다르게 해석됨

## 무엇을 쓰는가
- 문서에는 코드만 보고는 알 수 없는 것만 씀. 경계, 결정, 그 결정의 이유가 여기 해당함
- 코드와 설정을 보면 알 수 있는 구현 세부는 쓰지 않음
  - 예: 함수 이름, 설정 파일의 값, 실행 명령, 구현이 동작하는 순서
  - 구현 세부는 코드가 바뀔 때마다 문서와 갈라짐. 갈라진 문서는 없는 문서보다 나쁨
- lint, type check, 테스트가 강제하는 규칙은 목록을 반복하지 않음. 규칙이 왜 있는지만 씀
- 결정하지 않은 정책은 쓰지 않음
- 구현하지 않은 정책은 별도의 표시를 붙임
  - 규칙 하나가 미구현이면 규칙 앞에 `(미구현)` 라벨을 붙임. 예: "- (미구현) nocap은 ..."
  - 섹션 전체가 미구현이면 섹션 첫 줄에 `> [!NOTE]` 콜아웃으로 "이 섹션은 미구현임"을 씀
  - 명세 문서에는 표시하지 않음. 구현 여부는 nocap이 추적함
- 임시 대응과 현재 상황을 땜질하는 규칙은 문서가 아니라 PR 설명에 둠
- 같은 정보를 두 문서에 쓰지 않음. 다른 문서에 있는 정보는 링크로 참조함
- 코드를 바꿀 때 관련 문서도 같은 커밋에서 바꿈

## 형식
- frontmatter에는 `title`, `applies_to`를 두고, 필요할 때만 `read_when`, `related`를 둠
- 문서 간 링크는 상대 경로로 씀
- 규칙은 `-` 목록으로 씀. 규칙을 최상위 항목에, 이유를 그 아래 중첩 항목에 씀
- 절차는 번호 목록으로 씀. 한 단계에는 한 동작만 씀
- 섹션만 골라 읽어도 이해되도록 씀. 앞 섹션의 맥락이나 멀리 있는 대명사에 기대지 않음
- 코드 블록에는 언어를 표시함
- 날짜는 `YYYY-MM-DD` 형식으로 씀. "최근", "지난주" 같은 상대 표현을 쓰지 않음
  - 상대 표현은 문서를 읽는 시점에 따라 뜻이 바뀜
  - 외부 도구의 버전이나 지원 범위를 쓸 때는 확인한 날짜를 함께 씀

## Markdown 요소
- `##`는 문서의 주제 단위로 씀
- `###`는 `##` 섹션 안에 따로 참조될 하위 주제가 2개 이상일 때 씀
  - 헤딩은 링크 앵커와 목차가 됨. 헤딩이 거칠면 섹션 단위로 링크할 수 없음
- `####`는 쓰지 않음. 필요하면 문서를 나눔
  - GitHub 화면에서 `####`는 굵은 본문과 거의 구분되지 않음
  - 4단계가 필요하면 문서 하나가 주제를 너무 많이 다루는 것임
- 콜아웃은 `> [!WARNING]`과 `> [!IMPORTANT]`만 씀. 한 문서에 3개 이하로 씀
  - `WARNING`: 되돌릴 수 없는 작업. 예: npm publish
  - `IMPORTANT`: 놓치면 사고가 나는 제약
  - 콜아웃이 많으면 독자가 콜아웃을 건너뛰게 됨
  - 예외: 미구현 섹션 표시에는 `> [!NOTE]`를 씀
- 레이어, 의존 방향, 데이터 흐름처럼 구조를 설명할 때는 Mermaid 다이어그램을 씀
- 대부분의 독자가 건너뛰는 내용은 `<details>`로 접음. 예: 긴 예시
- 외부 자료의 출처와 확인 날짜는 각주 `[^1]`로 씀
- 굵게는 한 섹션에서 핵심어 2개 이하로 씀
- 체크리스트 `- [ ]`는 문서에 쓰지 않음
  - 체크리스트는 상태가 바뀌는 목록임. PR 템플릿이나 이슈에 둠

## 파일
- 파일 이름은 소문자 kebab-case로 씀. 예: `writing-guide.md`
- `README.md`, `AGENTS.md`, `CHANGELOG.md`, `LICENSE`는 관례에 따라 대문자로 씀
