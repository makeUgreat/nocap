# 코드 스타일

## 도메인 객체
- Parse, Don't Validate를 지향함. 입력을 검사하면 검사를 통과했다는 사실을 담은 타입으로 바꿈
  - 예: `SpecId.parse`는 ID 후보를 검사하고 통과하면 `SpecId`를 돌려줌. `SpecId`를 받는 코드는 ID 규칙을 다시 검사하지 않음
  - `boolean`만 돌려주는 검사는 결과를 타입에 남기지 않음. 값을 쓰는 곳마다 같은 검사를 반복하게 됨
- 생성할 때 지킬 불변식이 있는 값은 class로 만들고 생성자를 `private`으로 둠. 예: `SpecId`, `Location`
  - TypeScript는 구조적 타입을 씀. type이면 객체 리터럴로 불변식을 어긴 값을 만들 수 있음. `private` 생성자는 팩토리를 거치지 않은 값을 막음
- Tell, Don't Ask를 지향함. 객체의 상태를 꺼내 밖에서 판단하지 않음. 판단은 그 상태를 가진 객체가 함
  - 예: 명세 항목이 커버되었는지는 `Coverage`가 정함. 호출하는 쪽은 테스트 항목의 ID를 꺼내 명세 항목과 직접 비교하지 않음
  - 판단 규칙이 한 곳에만 있음. 상태를 읽는 쪽마다 규칙을 다시 계산하지 않음
- 도메인 규칙은 도메인 객체가 지킴. 파서는 입력 형식에서 읽은 사실만 넘김
  - 예: Markdown 파서는 HTML 주석마다 Markdown 트리에서 놓인 곳을 넘김. 테스트 파일 파서는 주석마다 걸친 줄과 같은 줄의 코드 여부를 넘기고, 테스트 단위가 시작하는 줄을 넘김
  - 예: 주석 덩어리를 모으는 일, 위치 이유를 정하는 일, 주석 본문의 태그 문법과 ID 규칙을 검사하는 일은 도메인 객체가 함
  - nocap 문법은 입력 형식이 바뀌어도 바뀌지 않음. 파서가 맡으면 입력 형식을 추가할 때마다 같은 규칙이 복사됨
  - 무엇이 테스트 단위인지는 파서가 정함. 테스트 프레임워크의 지식이고 nocap 문법이 아님
  - 놓인 곳이 트리 구조에서만 나오면 파서가 그 구조를 읽어 넘김. 예: 리스트 항목 첫 문단의 끝은 Markdown 트리 없이 알 수 없음

## 실패 처리
- 사용자 입력이나 실행 환경에서 온 실패는 결과 타입으로 돌려줌. 프로그램 버그로 생긴 실패는 예외로 던짐
  - 예: `SpecId.parse`는 규칙을 어긴 ID 후보에 `invalid-char`나 `invalid-whitespace`를 돌려줌. `FileReader.read`는 권한이 없으면 `read-error`를 돌려줌. `Location.of`는 빈 경로를 받으면 예외를 던짐
  - 사용자 문서의 오류와 파일 권한 문제는 예상할 수 있는 실패임. 결과 타입은 호출하는 쪽이 그 실패를 처리하게 강제함
  - 빈 경로 같은 값은 호출하는 코드의 버그임. 처리할 방법이 없으므로 바로 드러나게 함

## 주석
- 계약에만 TSDoc을 씀. 계약은 포트, 경계 타입, 유스케이스 결과, 그리고 다른 레이어가 `kind`로 분기하는 도메인 타입임
  - 계약은 구현하는 쪽과 쓰는 쪽이 코드를 열지 않고 약속을 확인하는 곳임. 계약이 아닌 코드에도 TSDoc이 있으면 약속과 구현 설명이 구분되지 않음
  - 계약이 아닌 코드에는 구현의 이유만 `//` 주석으로 씀
- TSDoc은 영어로 씀
  - 주석은 빌드된 `.d.ts`에 남아 사용자 IDE의 hover에 보임. 한글이면 한글을 읽지 못하는 사용자에게 계약이 전달되지 않음
- 타입의 설명은 타입 위에 한 번에 씀. 필드와 union 멤버마다 나눠 쓰지 않음
  - 필드마다 주석이 있으면 타입 하나를 읽을 때 설명이 여러 곳에 흩어짐
- 같은 값의 뜻을 두 계약에 쓰지 않음. 그 값을 가장 바깥에서 읽는 계약에 씀
  - 바깥 레이어는 안쪽 계약을 볼 수 없지만, 안쪽 계약을 읽는 쪽은 바깥 계약도 볼 수 있음
