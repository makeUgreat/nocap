# 테스트 작성 규칙

## 테스트 범위
- 명세 항목마다 [테스트 태그](syntax.md)가 붙은 테스트가 1개 이상 있어야 함
  - 이것은 최소 조건임. 테스트 전체는 이보다 넓음
- 명세 항목이 다루지 않는 동작도 테스트함. 이런 테스트에는 테스트 태그를 붙이지 않음
  - 예: 명세에 없는 입력 조건, 오류 처리, 명세 항목과 직접 연결되지 않는 공개 함수
  - 명세는 사용자에게 약속하는 동작만 담음. 코드가 올바른지는 그보다 많은 테스트로 확인해야 함
- 테스트 태그는 테스트 구조를 정하지 않음. 태그의 위치와 개수는 nocap 문법을 따름
  - nocap은 이미 짜인 테스트에 연결만 더함. 연결을 위해 테스트 구조를 바꾸지 않음

## 검증 범위
- 동작은 대상, 조건, 결과로 정의함
  - 대상: 공개 진입점 하나
  - 조건: 같은 결과를 내는 입력의 묶음 하나. 필요하면 전제 상태도 포함함
  - 결과: 그 조건에서 대상이 지키는 계약 하나. 반환값, 던지는 오류, 부수 효과 중 하나임
- `it()` 하나는 동작 하나를 검증함
- assertion이 여러 개이면 모두 같은 결과를 확인해야 함
  - 예: 반환한 목록의 길이와 각 항목의 ID를 함께 확인함
- 테스트는 private 구현이 아니라 공개된 동작의 결과를 검증함
  - 내부 구현을 바꿔도 동작이 같으면 테스트는 깨지지 않아야 함

## 테스트 케이스 고르기
- 규칙마다 지켜지는 쪽과 어기는 쪽을 함께 검증함
  - 예: 명세 태그가 있는 리스트 항목은 명세 항목이 되고, 명세 태그가 없는 리스트 항목은 명세 항목이 되지 않음
- 같은 결과를 내는 입력은 대표 하나만 검증함
  - 입력을 늘려도 새로 증명하는 것은 없음. 규칙이 바뀔 때 고칠 테스트만 늘어남
- 엣지 케이스는 빈 입력, 값의 경계, 형식이 어긋난 입력임
  - 예: 빈 문자열
- 값에 경계가 있으면 경계 바로 안쪽과 바로 바깥쪽을 검증함
  - 예: 1 이상이어야 하면 0과 1을 검증함

## 테스트 구조와 이름

| 단계 | 단위 | 쓰는 경우 |
|---|---|---|
| 테스트 파일 | 공개 진입점 하나. 예: 함수, 클래스, 유스케이스 | 항상 |
| 바깥 `describe()` | 명세 항목 하나, 또는 명세 항목이 아닌 기능 하나 | 항상 |
| 안쪽 `describe()` | 그 동작에 참여하는 공개 메서드 하나 | 공개 메서드가 2개 이상일 때만 |
| `it()` | 동작 하나 | 항상 |

- 명세 항목을 검증하는 바깥 `describe()`는 이름을 명세 요약으로 씀
- `it()` 이름은 "조건이면 결과다" 한 문장을 한글로 씀
  - 이름에 "그리고"가 들어가면 동작이 둘임. `it()`을 나눔
- `describe()`와 `it()`의 이름에는 ID를 쓰지 않음
  - ID는 테스트 태그에만 있어야 함. 이름에도 ID가 있으면 nocap이 어느 쪽으로 연결하는지 알기 어려움

```ts
// spec-document.markdown.parser.test.ts

// nocap: MD-001
describe('명세 태그가 있는 리스트 항목마다 명세 항목 생성', () => {
  it('명세 태그가 있는 리스트 항목이 2개이면 명세 항목 2개를 반환한다', () => {
    // ...
  })
})

describe('빈 문서', () => {
  it('빈 문자열이면 빈 목록을 반환한다', () => {
    // ...
  })
})
```

## 단위 테스트와 통합 테스트
- 단위 테스트는 프로세스 안에서 대상 코드만 실행함. 파일 시스템이나 외부 도구를 쓰지 않음
  - 예: 명세 파서 테스트는 문자열을 넣고 결과를 받음
- 통합 테스트는 파일 시스템이나 외부 도구를 실제로 씀
  - 예: dependency-cruiser 설정 테스트는 임시 파일을 쓰고 dependency-cruiser를 실행함
- `pnpm test`는 둘 다 실행함. `pnpm test:unit`, `pnpm test:integration`은 하나만 실행함

## 테스트 배치
- 단위 테스트 파일은 대상 파일 옆에 `<대상>.test.ts`로 둠. 예: `src/infrastructure/markdown/spec-document.markdown.parser.test.ts`
- 통합 테스트 파일은 `test/` 아래에 `<대상>.integration-test.ts`로 둠. 예: `test/dependency-cruiser/config.integration-test.ts`
  - 통합 테스트는 어댑터를 실제로 초기화하는 준비 코드가 늘어남. 이 코드를 `src/` 밖에 모음
- 통합 테스트의 디렉토리는 대상 파일의 경로에서 `src/`를 뺀 경로임
  - 예: `src/infrastructure/markdown/spec-document.markdown.parser.ts`의 통합 테스트는 `test/infrastructure/markdown/`에 둠
  - 예: `src/bin.ts`의 통합 테스트는 `test/bin/`에 둠. `dependency-cruiser/config.ts`의 통합 테스트는 `test/dependency-cruiser/`에 둠
  - 레이어와 어댑터의 경계는 `src/`가 이미 정함. `test/`가 같은 경로를 따르면 별도 분류 없이 대상 하나로 단위 테스트와 통합 테스트의 위치를 모두 앎
- 통합 테스트에서 어댑터나 도구를 준비하고 실행하는 코드는 같은 디렉토리의 `<대상>.support.ts`에 둠. 예: `test/dependency-cruiser/config.support.ts`
  - 테스트 파일에는 입력과 기대 결과만 남음
- 여러 대상의 통합 테스트가 함께 쓰는 준비 코드는 `test/support/`에 둠. 예: 임시 프로젝트 디렉토리를 만드는 `test/support/project.support.ts`
  - 한 대상의 디렉토리에 두면 다른 대상의 테스트가 그 대상에 의존하게 됨
- 통합 테스트가 읽는 입력 파일은 테스트 파일 옆의 `fixtures/`에 둠. 성공, 실패, 엣지 케이스마다 파일 하나로 나눔. 예: `test/infrastructure/markdown/fixtures/success.md`, `failure.md`, `edge.md`
  - 통합 테스트는 실제 파일 형태에서 여러 입력이 함께 동작하는지 확인함. 규칙 하나씩은 단위 테스트가 확인함
  - 결과가 같은 쪽끼리 묶으면 실패한 fixture 이름으로 어느 쪽이 깨졌는지 앎
